# GitHub 高星 AI coding 项目调研

研究对象覆盖 AI coding agent 和可运行的生成式开发工作台。星标会持续变化，下面关注可复用的产品机制和工程规模，而不是固定排名。

| 项目 | 主要问题 | 解决方式 | 结果与体验启示 |
|---|---|---|---|
| [OpenCode](https://github.com/anomalyco/opencode) | 开发者需要在终端持续完成多步编码任务 | 开源终端 agent、模型/提供方可切换、工具调用和会话状态 | 证明“模型无关 + 可观察工具循环”适合长期任务；Junior 需要同样清晰的候选状态和版本轨迹 |
| [OpenHands](https://github.com/OpenHands/OpenHands) | 复杂软件任务需要 agent 读写仓库、运行命令并迭代 | 沙箱运行时、事件流、工具和代理协作 | 规模接近平台而非单页 demo；Junior 应把确定性引擎和 AI 编排分层，避免 AI 直接拥有产品写权限 |
| [Cline](https://github.com/cline/cline) | IDE 中的代码修改需要用户可控、可回退 | 读写文件、终端和浏览器工具；逐步 diff 与人工批准 | 关键体验是“看得见每一步、能拒绝”；对应 Junior 的候选预览、接受/取消和过期检测 |
| [Aider](https://github.com/Aider-AI/aider) | 终端协作修改代码，需保持上下文和提交质量 | Git 感知的对话、仓库地图、增量编辑和测试反馈 | 小而专注的循环胜过一次性生成；Junior 应优先做稳定的参考→候选→检查循环 |
| [Bolt.new](https://github.com/stackblitz/bolt.new) | 普通用户想用自然语言快速得到可运行网页 | 浏览器内生成、运行、预览和迭代 | “生成后立即看到结果”降低门槛；Junior 的三维模型、清单和图纸必须在同一工作台即时联动 |
| [gpt-engineer](https://github.com/AntonOsika/gpt-engineer) | 从自然语言快速生成项目骨架 | 规格驱动的文件生成、可配置模型、CLI 工作流 | 适合早期探索，但缺少家具制造的领域约束；Junior 需要结构化领域模型和确定性检查补足 |

## 对齐结论

1. **规模**：这些项目都把模型调用、工具执行、状态、错误和回滚分成独立层；Junior 当前原型应保持单仓库、单进程，但边界要按平台级职责拆开。
2. **文本**：优秀项目会明确“正在生成、等待批准、已应用、失败、过期”。Junior 文案需要统一使用“参考、假设、候选、检查、确认、发布”六个状态词。
3. **体验**：结果必须可见、可编辑、可回退。AI 只产出候选，用户不需要理解 JSON；模型、检查、图纸和清单必须跟随同一版本。
4. **需要我们补上的领域壁垒**：加工特征坐标、连接跨件校验、材料纹理方向、图纸和清单的一致性，以及未知/不支持的诚实传播。
